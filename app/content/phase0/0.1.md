## Why this matters

Every later lesson assumes you can get code onto a board and read what it says back. The boot log you will read today is the same log you will read when a product resets in the field at 3 a.m.; engineers who can read it find faults in minutes.

## Prerequisites, hardware, time

- One ESP32-S3 N16R8 board and a USB data cable (many cables are charge-only)
- A computer with about 5 GB free
- 60 to 90 minutes, most of it the toolchain download

No wiring. No other parts.

## Build it first

Work through this list; your ticks are saved.

- [ ] Install one toolchain. ESP-IDF directly: `eim install -i v6.1`. Or PlatformIO: install the VS Code extension; it fetches its own ESP-IDF on the first build
- [ ] Open a terminal in `firmware/phase0/0.1-hello` (for ESP-IDF, one with its environment active)
- [ ] Plug the board in through the port marked UART or COM, if it has two
- [ ] Build, flash and open the monitor. ESP-IDF: `idf.py set-target esp32s3`, then `idf.py flash monitor`. PlatformIO: `pio run -e esp32s3 -t upload -t monitor`
- [ ] Find the three lines printed by your own code in the output
- [ ] Leave the monitor: `Ctrl+]` under ESP-IDF, `Ctrl+C` under PlatformIO

Every later lesson says “build and flash” and means either of these. The [toolchain cheatsheet](#sheets-toolchains) lists each command side by side.

The whole program:

```c
#include <stdio.h>
#include <inttypes.h>
#include "sdkconfig.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_chip_info.h"
#include "esp_system.h"

void app_main(void)
{
    esp_chip_info_t chip;
    esp_chip_info(&chip);

    printf("Hello from %s: %d core(s), silicon revision v%d.%d\n",
           CONFIG_IDF_TARGET, chip.cores, chip.revision / 100, chip.revision % 100);
    printf("Free heap: %" PRIu32 " bytes\n", esp_get_free_heap_size());

    for (int tick = 0; ; tick++) {
        printf("tick %d\n", tick);
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

After roughly forty lines of boot log, your own output appears. The revision and heap numbers vary by board:

```expected
Hello from esp32s3: 2 core(s), silicon revision v<major>.<minor>
Free heap: <a few hundred thousand> bytes
tick 0
tick 1
tick 2
```

If nothing appears, see “Common mistakes” at the end before changing any code.

## How it works

**Four kinds of chip.** The words are used loosely in job postings; this is what they mean.

| | What it is | Memory | Runs | Example |
| --- | --- | --- | --- | --- |
| MCU, microcontroller | CPU, RAM, flash and peripherals in one package | Kilobytes to a few megabytes | Bare metal or an RTOS | STM32F4, ATmega328 |
| MPU, microprocessor | A CPU that needs external RAM and storage | Hundreds of megabytes and up | Linux or another full OS | The chip in a Raspberry Pi |
| SoC, system on chip | A CPU plus radios or other large subsystems on one die | Either scale | Depends on the chip | ESP32-S3 (MCU-class), Jetson’s Orin (MPU-class) |
| FPGA | Logic you configure into a circuit, not a program you run | Not applicable | Your own digital design | Lattice iCE40 |

Your ESP32-S3 is an MCU-class SoC: a microcontroller with Wi-Fi and Bluetooth LE radios built in.

**What is inside your board.** “N16R8” is the module’s memory option: 16 MB of flash for code and files, 8 MB of PSRAM as extra, slower RAM. The chip itself has two Xtensa LX7 cores at up to 240 MHz and 512 KB of fast internal RAM. Confirm these in the ESP32-S3 Series Datasheet, section “Features”; reading that page is part of lesson 0.6.

Select any block to see what it is for and where the course returns to it.

::widget chip

**What the boot log is telling you.** Three programs run in sequence, and each prints its own section:

1. **ROM bootloader.** Code fixed in the chip at the factory. It prints why the chip reset and which boot mode the strapping pins selected, then loads the next stage from flash.
2. **Second-stage bootloader.** Built from ESP-IDF source along with your app. It prints its version, the flash settings and the partition table, then picks an application and loads its segments.
3. **Your application.** ESP-IDF start-up code initialises the heap, the clocks and FreeRTOS, starts a task called `main`, and that task calls your `app_main()`. Look for a line from `main_task` just before your “Hello”.

Step through the same sequence here, then find each stage in your own log.

::widget boot

So `app_main` is not where execution starts. It is a function called by a FreeRTOS task that the framework created for you, which is why `vTaskDelay` works inside it.

## Go deeper

Scroll back through the log and answer these from what is printed; write the answers in your notebook.

- [ ] What reset reason does the ROM report after you press the board’s reset button? After you unplug and replug it?
- [ ] How many partitions are listed, and at what offset does the application start?
- [ ] How large is the application image? Run `idf.py size` and find the same number.
- [ ] Comment out the `vTaskDelay` line, rebuild and flash. What changes after a few seconds, and what does the new message name?

That last experiment is your first watchdog reset. A task that never yields starves the idle task, and the task watchdog reports it. Lesson 2.10 covers watchdogs properly.

## When to use it, when not to

| You need | Reach for | Why |
| --- | --- | --- |
| A sensor node on a battery, wireless, under a few dollars | An MCU-class SoC such as the ESP32-S3 | Microamp sleep currents, instant start, deterministic timing |
| A camera pipeline at 30 frames per second with a large neural network | An MPU-class system such as a Jetson | Gigabytes of RAM, a GPU, Linux drivers |
| Sub-microsecond parallel signal processing | An FPGA | Hardware parallelism, no instruction-by-instruction execution |
| A user interface with a browser and a filesystem full of apps | An MPU running Linux | The software ecosystem |

The boundary you will explore in Phase 9: an ESP32-S3 can run a person detector in tens of milliseconds, but not a large vision model.

## Break it

Do each of these on purpose and record the exact message you get. These three faults account for most “my board is dead” posts.

- [ ] Build for the wrong chip: `idf.py set-target esp32`, build, and try to flash the S3. Read what the flasher reports, then set the target back.
- [ ] Open a second serial monitor while the first is running, then try to flash.
- [ ] Use a charge-only USB cable, if you own one, and note what your computer does and does not show.

## Common mistakes and interview angles

- **Nothing happens when flashing.** The cable is charge-only, or the board is on its native-USB port and your system needs a driver or a different port. Try the other USB connector if the board has two.
- **The port is busy.** Another program, usually a second monitor, holds the serial port.
- **Garbage characters in the monitor.** The monitor’s baud rate does not match the console’s. `idf.py monitor` reads the right value from the project; a separate terminal program does not.
- **Interview angle.** “Walk me through what happens between power-on and `main()`” is a standard opener. A good answer names the ROM, the bootloader, start-up code that sets up memory and clocks, and then the application, and says which of those you have changed in practice.
