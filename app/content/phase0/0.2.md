## Why this matters

On a team, nobody asks whether you can write a blink. They ask you to check out a repository, build it and tell them why the binary grew by 40 KB. The build system is the first tool of the job.

## Prerequisites, hardware, time

Lesson 0.1 done. One S3 board. 45 minutes.

## Build it first

You will change one configuration option and measure what it does to the binary.

- [ ] In `firmware/phase0/0.1-hello`, run `idf.py size` and write down the total image size
- [ ] Run `idf.py menuconfig`, open **Compiler options**, and change **Optimization Level** to “Optimize for size”
- [ ] Save, exit, run `idf.py build` and `idf.py size` again
- [ ] Record the difference in bytes
- [ ] Open `sdkconfig` in an editor and find the line that changed
- [ ] Run `idf.py size-components` and name the three largest components

Nothing in your C file changed, yet the binary did. That is the point.

## How it works

The steps above use `idf.py`. Under PlatformIO the same actions are `pio run -e esp32s3 -t size` and `pio run -e esp32s3 -t menuconfig`, and the generated file is `sdkconfig.esp32s3`; the [toolchain cheatsheet](#sheets-toolchains) has the full mapping. Everything below applies to both.

An ESP-IDF project is a small tree with a fixed shape:

| Path | What it is | Edit it? |
| --- | --- | --- |
| `CMakeLists.txt` | Declares the project and pulls in ESP-IDF’s build logic | Rarely |
| `main/` | Your application component: sources and its own `CMakeLists.txt` | Yes |
| `sdkconfig.defaults` and `sdkconfig.defaults.<target>` | The few options you chose, in version control | Yes |
| `sdkconfig` | Every option, generated from the defaults and menuconfig | No, and do not commit it |
| `build/` | Everything generated: objects, the map file, the final `.bin` | Never |
| `main/idf_component.yml` | Managed dependencies from the component registry | When you add a library |
| `platformio.ini` | Tells PlatformIO which boards to build for and that the sources are in `main/` | Only if you use PlatformIO |

The commands you will use every day:

| Command | Does |
| --- | --- |
| `idf.py set-target esp32s3` | Chooses the chip and regenerates the configuration |
| `idf.py menuconfig` | Edits configuration options interactively |
| `idf.py build` | Compiles what changed and links the image |
| `idf.py -p PORT flash monitor` | Writes the image, then shows serial output |
| `idf.py size`, `idf.py size-components` | Reports where flash and RAM went |
| `idf.py fullclean` | Deletes `build/` when the configuration is confused |

**Why two configuration files.** `sdkconfig` holds thousands of options, most of which you never chose. Committing it makes every diff noisy and ties the project to one chip. `sdkconfig.defaults` records only your decisions, and the per-target file (`.esp32s3`, `.esp32`) records the ones that differ by chip. Delete `sdkconfig`, rebuild, and it is recreated from them.

## Go deeper

- [ ] Open `build/hello.map` and search for `app_main`. Note its address and size.
- [ ] Find `CONFIG_ESPTOOLPY_FLASHSIZE` in `sdkconfig`. Which defaults file set it?
- [ ] Run `idf.py build` twice in a row and time the second run. Why is it fast?

The build is a chain: CMake generates Ninja rules, the compiler turns each `.c` into an object, the linker combines objects and libraries according to a linker script, and a final tool wraps the result in the image format the bootloader expects. Lesson 1.1 opens the map file properly.

## When to use it, when not to

| Situation | Do this |
| --- | --- |
| An option every build of this project needs | Put it in `sdkconfig.defaults` |
| An option that differs between the S3 and the classic ESP32 | Put it in `sdkconfig.defaults.<target>` |
| An experiment for the next ten minutes | `idf.py menuconfig`, and do not save it into the defaults |
| The build behaves strangely after switching targets | `idf.py fullclean`, then build |

## Break it

- [ ] Add `CONFIG_ESPTOOLPY_FLASHSIZE_32MB=y` to `sdkconfig.defaults.esp32s3`, delete `sdkconfig`, build and flash. Read what the bootloader reports about the flash size, then undo it.
- [ ] Rename `main/hello_main.c` without updating `main/CMakeLists.txt`. Read the error from top to bottom and find the first line that names the real problem.

## Check yourself

1. Which file do you commit: `sdkconfig` or `sdkconfig.defaults`? Why?
2. What does `idf.py set-target` change that `idf.py build` does not?
3. Where would you look to learn which component is using the most flash?

## Common mistakes and interview angles

- **Editing `sdkconfig` by hand and committing it.** It will be overwritten, and reviewers will not thank you.
- **Forgetting `set-target`.** The build succeeds for the wrong chip and the flasher refuses it.
- **Interview angle.** “How do you keep debug and release builds apart?” A good answer mentions separate defaults files or build directories, and that optimisation level changes timing, which changes bugs.
