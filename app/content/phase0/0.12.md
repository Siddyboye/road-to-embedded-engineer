## Why this matters

Sensors hand you integers that mean fractions. Small processors do float arithmetic slowly or not at all, and a quantized neural network is fixed-point arithmetic in a long coat. And every byte you send over a wire can arrive wrong, so every real protocol carries a check.

## How it works

**Floating point** stores a sign, an exponent and 24 bits of precision. The precision is relative: about seven significant decimal digits wherever the value sits. That makes it convenient and gives it three traps. Most decimal fractions are not exact. Large values lose the ability to represent small steps. And comparing two floats for equality after arithmetic usually fails.

**On a microcontroller**, a `float` is cheap only if the chip has a floating-point unit. Your ESP32-S3 has a single-precision one; `double` is done in software and is much slower. Many smaller chips have neither.

**Fixed point** is an integer with an agreed scale. In Q8.8 the stored integer is the real value times 256. Addition is ordinary addition. Multiplication needs one shift afterwards:

```c
typedef int16_t q8_8_t;
#define Q(x)  ((q8_8_t)((x) * 256.0f + ((x) >= 0 ? 0.5f : -0.5f)))

static inline q8_8_t q_mul(q8_8_t a, q8_8_t b)
{
    return (q8_8_t)(((int32_t)a * b) >> 8);     /* widen first, then rescale */
}
```

The step is constant, the cost is integer arithmetic, and overflow is yours to prevent. Sensor datasheets speak fixed point constantly: “divide the raw value by 16384 to get g” is Q2.14.

**Checksums and CRCs.** A checksum adds the bytes up; it is cheap and misses reordered bytes and many double errors. A CRC treats the message as one long binary number and keeps the remainder of dividing it by a fixed polynomial. It catches every single-bit error, every burst shorter than its width, and almost everything else. Two ends must agree on five things, not one: the polynomial, the starting value, whether bytes are bit-reversed going in, whether the result is reversed, and a final XOR. That is why the same polynomial appears under several names.

## When to use it, when not to

| Need | Use |
| --- | --- |
| Quick arithmetic on a chip with an FPU, modest precision | `float` |
| Money, counters, timestamps, anything compared for equality | Integers |
| DSP or ML on a chip without an FPU, or for speed and determinism | Fixed point |
| Detecting a corrupted frame | CRC; 8 bits for short frames, 16 or 32 for longer ones |
| Detecting deliberate tampering | Not a CRC: a cryptographic MAC (lesson 5.10) |

## Common mistakes and interview angles

- **`==` on floats.** Compare against a tolerance, or use integers.
- **`double` by accident.** An unsuffixed constant such as `0.1` is a double in C; write `0.1f`.
- **CRC mismatch.** Almost always the reflect or initial-value setting, not the polynomial.
- **Interview angle.** “Implement a CRC” or “why not just use a checksum?” Know one concrete failure a checksum misses: two swapped bytes.
