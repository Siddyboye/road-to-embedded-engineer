## Why this matters

“It works, but it feels slow”, “it drops a sample every few seconds” and “it hangs when the sensor is unplugged” are timing-design faults, not coding faults. This lesson gives you the vocabulary to design them out.

## How it works

**Latency and throughput.** Latency is how long one thing takes from cause to effect. Throughput is how many things get done per second. They pull against each other: batching ten samples before processing raises throughput and makes the first sample wait. A control loop cares about latency; a data logger cares about throughput. Decide which you are building.

**Blocking and busy-waiting.** A busy-wait keeps the CPU spinning until time passes. Nothing else at the same or lower priority can run, the idle task cannot run, and the watchdog you just triggered is the system telling you so. A blocking delay hands the CPU back to the scheduler until the time is up. On a battery the difference is also power: the idle task is what lets the chip sleep.

**The tick.** The scheduler measures time in ticks, 10 ms each by default in ESP-IDF. `vTaskDelay(pdMS_TO_TICKS(25))` waits 2 ticks, not 25 ms, and `pdMS_TO_TICKS(5)` is zero. For anything finer than a tick you need a hardware timer.

**Two kinds of clock.** *Monotonic* time counts up from boot and never jumps: use it for intervals, timeouts and scheduling. *Wall-clock* time is the date and time of day; it is set from outside, by a network or a user, and can jump forwards or backwards when corrected. Measuring an interval with wall-clock time is a bug that appears on the day the clock is adjusted.

**Timeouts.** Any wait for something outside your control (a sensor, a network, a human) must have a limit and a plan for when the limit passes. A loop that waits for a pin to go high is a hang waiting for a loose wire.

```c
int64_t start = esp_timer_get_time();            /* microseconds since boot, monotonic */
while (gpio_get_level(ECHO_GPIO) == 0) {
    if (esp_timer_get_time() - start > 30000) {  /* 30 ms: no echo is coming */
        return ESP_ERR_TIMEOUT;
    }
}
```

**Under the hood.** `esp_timer_get_time()` reads the 64-bit SYSTIMER counter and divides by 16; `vTaskDelay` parks the task on the delayed list; `esp_rom_delay_us` spins in ROM. Lesson 0.14 follows each of them to the hardware, and the [under-the-hood cheatsheet](#sheets-under-the-hood) keeps the rows.

## When to use it, when not to

| Waiting for | Use | Never |
| --- | --- | --- |
| A fixed, long interval | `vTaskDelay` | A busy loop |
| An event from an interrupt | Block on a queue or notification with a timeout (Phase 4) | Polling a flag in a tight loop |
| A pin, inside a protocol, for microseconds | A bounded busy-wait | An unbounded one |
| A date and time | Wall-clock time | Wall-clock time for measuring intervals |

## Common mistakes and interview angles

- **A wait with no timeout.** The most common cause of a device that “freezes sometimes”.
- **Treating the tick as a millisecond.** It is whatever the configuration says.
- **Interview angle.** “Why is `delay()` considered bad practice?” Separate the two cases: a busy-wait is harmful; a blocking delay is fine but coarse and must never be how you measure time.
